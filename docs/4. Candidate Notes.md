## 1. Elevator Pitch

The deliverable is a complete, executed comparison of **three generations of retrieval technology** - BM25 keyword search, Word2Vec static embeddings, and sentence-transformer semantic search - on the Natural Questions dataset, with IR metrics (Recall@k, Precision@k, MRR) implemented **from scratch**, a hyperparameter optimizer for the weakest retriever, an executed analysis notebook, and an interactive Streamlit RAG demo. │   mrr            = 1/rank of first relevant doc, 0.0 if none                  │

### Key Design Decisions

| Decision | Rationale |
| :--- | :--- |
| **One retrieval contract for all three methods** | Every retriever returns `{query_index: [doc_id, ...]}` ranked best-first, with `results[q_idx] = top_k_indices.tolist()`. The evaluator, notebook and Streamlit app were written against that contract once and work unchanged with any retriever - which is exactly the swap-ability a RAG system needs. |
| **Metrics implemented from scratch as pure math** | `recall_at_k` / `precision_at_k` / `mrr` use set intersections and `1/rank` with no metric library, so grading can verify the logic line by line. Queries absent from `qrels` are skipped; queries with zero relevant documents are skipped in recall (avoids ÷0) but score 0.0 in precision when `k == 0`. |
| **Precision divides by k, not by len(retrieved)** | `Precision@5` must be comparable across methods even when a corpus is smaller than k; dividing by the requested cutoff keeps the denominator fixed, matching the standard IR definition. |
| **MRR breaks at the first relevant document** | Reciprocal rank only cares about the *first* hit - the rank a RAG user experiences when scanning results top-down. Appending `rr = 0.0` when nothing relevant is found keeps per-query scores in `[0, 1]` so `np.mean` is a true mean. |
| **Symmetric BM25 tokenization** | Query and documents use the identical `lower().split()` tokenization; mismatched tokenization is the classic silent BM25 bug and would have depressed the baseline. |
| **Zeros vector fallback in Word2Vec** | `_text_to_vector` returns `np.zeros(vector_size)` when no word is in vocabulary, so `cosine_similarity` stays well-defined and `corpus_vectors` is always a dense `np.ndarray` - a `None` there would crash every query. |
| **MRR drives the Word2Vec grid search** | `optimize_parameters()` initializes `best_score = -1.0` so the first configuration always records a baseline, logs every attempt (`config`, `mrr`, `recall_5`, `metrics`) for auditability, and selects by MRR - the metric that matches how users scan a ranked list. Skip-gram (`sg=1`) with `window=20` won, which makes sense for a 2,440-document corpus where context is scarce. |
| **Encoder settings fixed and explicit** | `batch_size=32`, `convert_to_numpy=True`, `show_progress_bar` only for the (one-time) corpus encode. Embeddings are numpy arrays of shape `(n_docs, 384)`, satisfying the rubric's shape requirement directly. |
| **Per-query cosine similarity loop** | `cosine_similarity(q_emb.reshape(1, -1), corpus_embeddings)[0]` - the `[0]` squeezes sklearn's `(1, N)` output to 1-D before `argsort`; forgetting it is the most common silent shape bug in this pattern. |
| **Streamlit RAG is opt-in** | The demo's "Enable RAG Answers" checkbox defaults to whether an API key exists, so the retrieval comparison works with zero credentials, and the OpenAI generation path is exercised only when explicitly enabled. |

## 3. System-Level RAG Explanation

> This section answers the rubric criterion *"Notebook or README includes a written explanation of how the retriever supports a RAG pipeline"*. The same explanation was added as a markdown cell at the end of `notebooks/unified_retrieval_comparison.ipynb` (cell 25, "How This Retriever Powers a RAG Pipeline"). The README was left as delivered, per the working constraints.

### How the Retriever Feeds the Generator

Everything benchmarked in this project is the **retrieval half of a RAG (Retrieval-Augmented Generation) system**. In a RAG pipeline, the retriever **selects the relevant documents that the generator consumes**:

1. **Retrieval** - given the user's query, a retriever (BM25, Word2Vec, or a sentence transformer) scores every document in the corpus and returns the **top-k most relevant** documents. This is exactly what each `retrieve()` method implements: a mapping from every query to a ranked list of document IDs.
2. **Augmentation** - the retrieved documents are concatenated with the original query into a single prompt, giving the language model context it was never trained on (private documents, recent events, domain knowledge).
3. **Generation** - an LLM reads that augmented prompt and writes an answer **grounded in the retrieved documents** instead of relying on parametric memory alone.

The retriever is the bottleneck of the whole pipeline: **the generator can only use documents the retriever selected**. If the relevant document is not inside the top-k, the LLM cannot recover it - it either answers without evidence or hallucinates. That is why Recall@k, Precision@k and MRR are the right yardsticks here: they quantify how reliably a retriever puts the right documents in front of the generator. In the Streamlit demo, this exact flow is visible per query: each retriever's top-3 documents are displayed next to the optional LLM answer generated from them (`streamlit/rag_system.py`).

### From Keyword Search to Semantic Search

| Generation | Method | How it matches query ↔ document | Weakness in a RAG pipeline |
| :--- | :--- | :--- | :--- |
| 1st | **BM25** (keyword) | Exact term overlap with TF-IDF-style weighting | Vocabulary mismatch: fails on synonyms, paraphrases, unseen phrasings |
| 2nd | **Word2Vec** (static embeddings) | Mean word vector; words have neighbors, but **one vector per word regardless of context** | No context sensitivity; weak on small corpora (0.0233 baseline MRR here) |
| 3rd | **Transformers** (contextual embeddings) | Full-sentence bi-encoder similarity, context-aware | Needs an offline index build; slower per query |

The measured results on Natural Questions (2,440 documents, 2,000 queries) show why production RAG moved from keywords to semantics:

| Metric | BM25 (keywords) | Word2Vec (tuned) | Transformer MiniLM-L6-v2 (semantic) |
| :--- | :--- | :--- | :--- |
| Recall@5 - is the evidence in the context window? | 0.7266 | 0.7641 | **0.9298** |
| MRR - how high does the first relevant doc rank? | 0.6738 | 0.6978 | **0.9044** |
| Precision@5 - is the context mostly relevant? | 0.1751 | 0.1876 | **0.2263** |

Read from a RAG perspective: with a BM25 retriever, ~27% of queries **never** place the gold document inside the top-5 context window, so the LLM is forced to answer without its evidence. The transformer retriever raises that coverage to ~93% - and in the notebook's 10-query qualitative spot-check, the correct document was retrieved at rank 1 for **9/10** transformer queries versus **4/10** for BM25. The tuned Word2Vec retriever sits in between (MRR 0.6978) after hyperparameter optimization lifted it from a 0.0233 baseline - a reminder that static embeddings need careful tuning before they are usable as a RAG retriever.

This retrieve-then-generate design is the architecture behind **real-world systems**: **Perplexity** grounds every generated sentence in numbered retriever citations; **ChatGPT** (file search, web browsing) and **GitHub Copilot Chat** retrieve documents or code into the prompt before the model writes; enterprise assistants such as Azure OpenAI "on your data" and AWS Bedrock Knowledge Bases retrieve from an internal index where the retriever component is swappable - exactly like the three classes compared in this project.

**Key takeaway:** upgrading the retriever is the cheapest way to upgrade a RAG system - switching BM25 → MiniLM lifted Recall@5 by ~20 points and MRR by ~0.23 in this benchmark, before changing a single token of the generator's prompt.

## 4. IR Principles in Practice

**Recall@k is the RAG-critical metric.** A RAG generator can only use evidence that made it into the prompt, so Recall@5 answers the only question that matters first: *did the evidence survive retrieval?* BM25's 0.7266 means more than a quarter of Natural Questions queries reach the LLM with no gold document at all; the transformer's 0.9298 leaves that failure mode for ~7% of queries.

**Precision@5 punishes context stuffing.** Natural Questions has exactly one relevant document per query in this setup, so Precision@5 is capped near 0.2 by construction - the numbers (0.1751 / 0.1876 / 0.2263) mainly confirm that the transformer wastes less of the context window on distractors. Reading it in isolation would mislead; read it against the dataset's relevance structure.

**MRR models the user, not the system.** `1/rank` of the first relevant document rewards rank-1 hits quadratically more than rank-10 ones, matching how a RAG prompt builder and a human both scan results. It is also the metric that made the Word2Vec optimizer meaningful: a config could raise Recall@10 while leaving the first relevant document buried.

**Metrics from scratch must define "relevant" explicitly.** All three functions treat a document as relevant iff `qrels[q_id][doc_id] > 0` and skip queries absent from `qrels`. Those two lines are the difference between a metric and a guess, and they are where metric-library black boxes hide their assumptions.

**Tuned numbers carry selection bias - state it.** The Word2Vec 0.6978 MRR was selected, on the same 2,000 queries used for reporting, as the best of 10 configurations; BM25 and MiniLM report untuned, single-configuration numbers. The Word2Vec figure is therefore an optimistic estimate of its generalization, and the honest comparison is that even *tuned* static embeddings do not reach the *untuned* transformer.

**Claims stay inside the evidence.** All numbers describe a 2,440-document, 2,000-query teaching subset of Natural Questions executed on CPU - not a production corpus, and not the GPU the machine owns. The sentence-transformer log line in the executed notebook reads `No device provided, using cpu`; embedding quality is device-independent, but the quoted timings (e.g., MPNet's 206.5 s index build) are CPU timings, not GPU timings.

## 5. AI Collaboration Playbook

The deliverable was four modules whose holes had to be filled without touching scaffold code, a 20-test suite, an executed notebook and a working demo - so the workflow was built around **inspect → repair → implement → test → execute → smoke-test → verify**.

The workflow was:

1. **Read the real scaffold in plan mode before writing anything.** All four files, their line numbers and their surrounding scaffolds were read first; the implementation plan matched the actual `YOUR CODE HERE` blocks 1:1, so no hole was discovered mid-edit.
2. **Audit the environment before trusting the brief.** The brief said `.venv` was pre-installed; the project actually had `venv\` containing only `pip`, and the global Python 3.14 lacked `rank_bm25`, `gensim`, `sentence-transformers` and `transformers`. The discrepancy was surfaced and approved before any install.
3. **Repair the environment along the path of least damage.** Missing pure-Python/wheel packages went into the existing global interpreter first; when `gensim` proved uninstallable on Python 3.14, the decision escalated to installing Python 3.12.10 (winget) and building a clean `.venv312` rather than patching C code.
4. **Implement against the tests, not against hope.** All four modules were filled in one pass; `py_compile` verified syntax; `pytest tests/test_evaluator.py` (pure math, no heavy deps) validated the evaluator before any model download; then the full suite ran to **20 passed**.
5. **Execute, then read the executed notebook.** `python -m nbconvert --to notebook --execute` produced the executed copy; a programmatic pass over its JSON confirmed **zero error outputs** and extracted every number quoted in these notes (per-method metrics, optimizer log, model comparison timings).
6. **Smoke-test the demo twice, not once.** Streamlit's `AppTest` ran the app script headless (initial render + a real query) and found 0 exceptions; a real `streamlit run` server then returned `200 ok` on `/_stcore/health`.
7. **Verify against the rubric, not just the tests.** A final pass over `docs/3. Rubric.md` checked all five criteria and found one gap - the written RAG-pipeline explanation - which was then fixed where allowed.

The collaboration principle was the same as in P2: **verify, don't trust.** Every figure in these notes was read from an executed test run, a saved notebook stream or an HTTP status line, and the brief's environment assumptions were treated as hypotheses to check, not facts to build on.

## 7. Challenges and Resolutions

### Challenge 1 - The project virtual environment was empty

**What happened:** The brief stated `.venv` was pre-created with all packages installed. The project directory actually contained `venv\` (not `.venv\`), and `pip list` inside it showed exactly one package: `pip`. The global Python 3.14.7 had `numpy`, `scikit-learn`, `torch` and `pytest`, but lacked `rank_bm25`, `gensim`, `sentence-transformers` and `transformers`. No test beyond the evaluator could even be collected.

**Resolution:** Surfaced the discrepancy and got approval to install. `rank-bm25`, `sentence-transformers` and `transformers` installed into the global interpreter (they reuse the existing torch); the evaluator (5/5), BM25 (5/5) and transformer (5/5) suites then passed on 3.14. `gensim` remained the blocker and got its own challenge.

### Challenge 2 - gensim has no Python 3.14 wheel and will not build

**What happened:** `pip install gensim` on Python 3.14 fell back to a source build and failed in the MSVC compile: the Cython-generated C references APIs removed or changed in 3.14 (`ma_version_tag`, `_longobject.ob_digit`, `_PyLong_AsByteArray` signatures), producing dozens of C2061/C2039 errors. A wheel check confirmed **no cp314 wheel exists for any modern gensim** (only ancient 0.x releases), and the machine had no conda or usable 3.13 (the Python313 folder had no `python.exe`).

**Resolution:** Installed **Python 3.12.10** via winget (verified a `gensim-4.4.0-cp312-cp312-win_amd64.whl` exists first), created a clean project venv **`.venv312`**, and installed the full dependency set there (`gensim 4.4.0`, `torch 2.15.0`, `transformers 5.22.2`, `sentence-transformers 6.2.0`, `beir 2.2.0`, `streamlit`, `jupyter`, `pytest`). All remaining work - tests, notebook execution, demo - ran in that venv. The stale `venv\` was left untouched.

### Challenge 3 - The jupyter launcher dispatched to the wrong interpreter

**What happened:** Running `.venv312\Scripts\jupyter.exe nbconvert --execute` crashed with `ModuleNotFoundError: No module named 'beir'` - from a traceback pointing at **Python 3.14's site-packages**. `jupyter.exe` had resolved the `jupyter-nbconvert` subcommand through `PATH`, which found the global 3.14 install before the venv.

**Resolution:** Invoked the tool through the venv interpreter directly: `.venv312\Scripts\python.exe -m nbconvert ...`, and pinned the kernel with `--ExecutePreprocessor.kernel_name=python3` so the execution kernel also came from the venv. The notebook then ran with `beir`, `gensim` and `sentence-transformers` all resolving from `.venv312`.

### Challenge 4 - Windows console encoding broke every emoji print

**What happened:** The retrievers and the Streamlit app `print()` emoji (🔧 ✅ 🔍). Under the default cp1252 console, both `AppTest` and a plain print of app titles failed with `UnicodeEncodeError: 'charmap' codec can't encode character '\U0001f527'`. The first AppTest run *failed the app* - the exception surfaced inside `initialize_retrievers()` at the first emoji print, which looked like an app bug but was pure I/O encoding.

**Resolution:** Set `PYTHONUTF8=1` and `PYTHONIOENCODING=utf-8` for every shell invocation (the notebook itself was immune because Jupyter runs UTF-8). With UTF-8, the identical AppTest passed end to end. The practical instruction for running the demo on this machine is documented: set the two variables before `streamlit run`.

### Challenge 5 - The Word2Vec baseline collapsed on the small corpus

**What happened:** The notebook's first Word2Vec configuration (vector_size 200, window 10, CBOW defaults) scored **MRR 0.0233 / Recall@5 0.0313** on 2,440 documents - document vectors that barely separate relevant from irrelevant, near-random retrieval.

**Resolution:** This is precisely what `optimize_parameters()` exists for. The grid search over 10 configurations, selecting by MRR, found `{'vector_size': 100, 'window': 20, 'min_count': 2, 'sg': 1, 'epochs': 100}` at **MRR 0.6978 / Recall@5 0.7641** (+2,893.9% / +2,338.6%). Skip-gram with a wide context window is the right family for a tiny corpus, and the results log in the notebook shows the full trajectory (every configuration's MRR is recorded, including the two that scored below 0.12).

### Challenge 6 - The rubric required a written RAG explanation that neither artifact contained

**What happened:** The rubric criterion *"Notebook or README includes a written explanation of how the retriever supports a RAG pipeline"* has five submission requirements. Verification found: no RAG, generator, or LLM-product mention anywhere in the notebook's markdown cells (case-insensitive grep); and in the README only a three-line R-A-G bullet glossary plus generic application categories - **no named real-world system** (Perplexity/Copilot/ChatGPT) and no actual written explanation of retriever → generator. Three of five requirements failed or were borderline.

**Resolution:** Added a dedicated markdown cell to `notebooks/unified_retrieval_comparison.ipynb` ("🔗 How This Retriever Powers a RAG Pipeline") covering all five requirements: the retriever selects the top-k documents the generator consumes; retrieval → augmentation → generation; named systems (Perplexity, ChatGPT, GitHub Copilot, enterprise RAG); the BM25 → Word2Vec → transformer evolution; and the measured three-method comparison with the numbers from the executed run. The same explanation is Section 3 of this document. The README was deliberately left as delivered, per the working constraint.

## 11. Retrospective

### What I'd Do Differently

1. **Create the isolated 3.12 venv before touching the global interpreter.** Installing the first missing packages into global Python 3.14 upgraded shared dependencies and left pip-reported conflicts with unrelated tools (`litellm`, `google-adk`). Discovering the gensim incompatibility *before* any install would have made `.venv312` the first and only environment change.
2. **Install the CUDA torch build in `.venv312` from the start.** The benchmark ran on CPU; MPNet's 206.5 s index build and the notebook's wall clock would shrink substantially on the 4 GB Ada GPU, and MiniLM (~90 MB) fits trivially in VRAM.
3. **Split tuning and evaluation query sets for the Word2Vec optimizer.** Selecting the best of 10 configs on the same queries used for reporting inflates the tuned number; a held-out query split would make the 0.6978 an unbiased estimate.
4. **Seed gensim in the retriever.** Word2Vec training is stochastic and the retriever sets no seed, so Word2Vec metrics wiggle between runs while BM25/transformer numbers are deterministic. A one-line `seed=` in the constructor would make the whole notebook reproducible.
5. **Author the RAG explanation during initial notebook work, not during verification.** The gap was only visible when scoring the rubric as a grader would; building that pass into the authoring step would have saved a revision cycle.

### What Worked Well

1. **Reading the scaffold in plan mode first.** The implementation plan matched the actual `YOUR CODE HERE` blocks 1:1; every edit was a surgical placeholder replacement, and no scaffold line or signature moved.
2. **One retrieval contract, three implementations.** Because all retrievers return `Dict[int, List[int]]`, the evaluator, notebook and Streamlit app consumed them with zero adaptation code - the property the rubric's "Complete Retrieval System Implementation" criterion is really testing.
3. **Mechanical rubric scoring.** Mapping each submission requirement to concrete evidence (test names, grep hits, executed streams) is what surfaced the RAG-explanation gap that a "tests are green" mindset would have missed.
4. **Two-level demo smoke testing.** `AppTest` exercised the app logic (and caught the console-encoding failure in a way a human click-through would have misread), while the headless server check verified the real launch path - together they covered both failure classes.
5. **Environment honesty.** Recording that the benchmark ran on CPU, that the tuned Word2Vec number carries selection bias, and that the global interpreter took side-effect upgrades keeps these notes trustworthy rather than promotional.

### The AI Partnership

> "The value of the AI partnership here was verification discipline over generation speed. The coding pass filled all four modules correctly on the first attempt - but the environment the brief described did not exist, and the difference between 'tests pass' and 'the submission meets the rubric' only appeared when the artifacts were scored mechanically against `docs/3. Rubric.md`. The planner read the scaffold before writing, the executor repaired the environment (Python 3.12 via winget, a clean `.venv312`, an executed notebook) without touching scaffold code, and the verification pass then caught the one thing no test could catch: a missing written explanation of how the retriever feeds the generator. The human role was approving environment changes, accepting the CPU-vs-GPU trade-off, and deciding that fixing the rubric gap in the notebook and candidate notes - while leaving the README untouched per the working constraints - was the right scope."

### Final Thoughts

This project was less about inventing retrieval algorithms and more about making three generations of them run, measurably, inside one pipeline under real constraints: an empty starter venv, a Python version one release too new for gensim, a CPU-only execution path, and a rubric that graded explanations as well as code. The numbers tell the field's story cleanly - BM25's 0.6738 MRR is a strong zero-training baseline that still misses the evidence entirely for ~27% of queries, tuned Word2Vec closes most of the gap at 0.6978, and a 23M-parameter sentence transformer reaches 0.9044 with 93% context coverage. Those are not just benchmark figures; they are the direct input to RAG answer quality, because a generator can only use what the retriever selected. All 20 tests pass, the executed notebook contains zero errors and now also contains the system-level explanation the rubric asks for, and the demo runs - verified, not assumed.
